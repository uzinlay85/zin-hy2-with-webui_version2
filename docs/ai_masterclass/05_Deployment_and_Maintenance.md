# Chapter 5: 🚀 Deployment, Maintenance & Version Control

Developer တွေဆီမှာ အဖြစ်အများဆုံး စကားတစ်ခွန်းရှိပါတယ်။ *"ငါ့စက်ထဲမှာတော့ အလုပ်လုပ်တယ် (It works on my machine)"* ဆိုတာပါပဲ။ ကိုယ့်စက်ထဲမှာ ရေးထားတဲ့ Code ကို အင်တာနက်ပေါ်က ဆာဗာ (Production) ပေါ် တင်တဲ့အခါမှာ သတိထားရမယ့် အချက်တွေ ရှိပါတယ်။

## ၁။ Local vs Production (ကိုယ့်စက် နှင့် ဆာဗာ)

- **Local Environment:** ကိုယ့်ကွန်ပျူတာထဲမှာ စမ်းသပ်ရေးသားတဲ့ အဆင့်ပါ။ ဒီအချိန်မှာ Error တက်ရင် အကုန်လုံး အသေးစိတ် မြင်ရဖို့ (Debug Mode) ဖွင့်ထားလေ့ ရှိပါတယ်။ (ဥပမာ - FastAPI မှာ `--reload` သုံးတာမျိုး)။
- **Production Environment:** လူအများ တကယ်သုံးမယ့် ဆာဗာပေါ် တင်တဲ့အဆင့်ပါ။ ဒီအချိန်မှာ လုံခြုံရေးအရ Error အသေးစိတ်တွေကို ဖုံးကွယ်ထားရပါမယ်။ Debug Mode ကို လုံးဝ (လုံးဝ) ပိတ်ထားရပါမယ်။ စွမ်းဆောင်ရည် အကောင်းဆုံး ဖြစ်အောင် ချိန်ညှိရပါမယ်။

## ၂။ Process Managers ဖြင့် အသက်သွင်းခြင်း

Terminal မှာ Code ကို ဖွင့်ထားရင် Terminal ပိတ်လိုက်တာနဲ့ App ပါ သေသွားပါမယ်။ ဆာဗာမှာ အမြဲတမ်း ရှင်သန်နေအောင် **Process Managers** တွေကို သုံးရပါတယ်။

- **Linux Systemd:** ကျွန်တော်တို့ ပရောဂျက်မှာ သုံးထားတဲ့ နည်းလမ်းပါ။ Linux OS ရဲ့ မူလစနစ်ဖြစ်လို့ အသေချာဆုံးနဲ့ အခိုင်မာဆုံးပါ။ `systemctl start hy2-panel`, `systemctl enable hy2-panel` လို့ ရိုက်လိုက်ရုံနဲ့ ဆာဗာ ပိတ်သွားလို့ ပြန်ဖွင့်ရင်တောင် အလိုအလျောက် ပြန်တက်လာပါလိမ့်မယ်။
- **PM2 / Supervisor:** Node.js ပရောဂျက်တွေမှာ PM2 ကို အသုံးများပါတယ်။ Python မှာတော့ Supervisor (သို့) Systemd ကို အသုံးများပါတယ်။

## ၃။ Version Control (Git နှင့် GitHub အသုံးဝင်ပုံ)

Code တွေကို Folder တွေနဲ့ `project_final`, `project_final_real`, `project_new` ဆိုပြီး နာမည်ပေး သိမ်းမယ့်အစား Git ကို သုံးတာ အကောင်းဆုံးပါ။

- **အချိန်စက် (Time Machine):** မှားသွားရင် အရင်အကောင်းအတိုင်း ရှိနေခဲ့တဲ့ အချိန်ကို စက္ကန့်ပိုင်းအတွင်း ပြန်သွား (Revert / Reset) လို့ ရပါတယ်။
- **အဖွဲ့လိုက် အလုပ်လုပ်ခြင်း:** လူ ၅ ယောက် ရေးနေရင်တောင် ဖိုင်တွေ ထပ်မသွားအောင် ပေါင်းစပ် (Merge) လုပ်ပေးနိုင်ပါတယ်။
- **Backup:** GitHub ပေါ်မှာ သိမ်းထားတဲ့အတွက် ကိုယ့်စက် ပျက်သွားရင်တောင် Code တွေ လုံးဝ မပျောက်တော့ပါဘူး။

**💡 AI နဲ့ ရေးတဲ့အခါ အကောင်းဆုံး အလေ့အကျင့် (Best Practice):**
AI ကို ခိုင်းလို့ အပိုင်းတစ်ခု အောင်မြင်သွားပြီ (ဥပမာ - Login ရေးလို့ ပြီးသွားပြီ) ဆိုတာနဲ့ ချက်ချင်း `git commit -m "feat: add login system"` ဆိုပြီး မှတ်တိုင် ထူလိုက်ပါ။ ပြီးမှ နောက်တစ်ပိုင်း ဆက်ခိုင်းပါ။ အကုန်လုံး ပြီးမှ တစ်ပြိုင်နက်တည်း Commit လုပ်တာမျိုး ရှောင်ပါ။

## ၄။ CI/CD (Continuous Integration / Continuous Deployment) သဘောတရား

တကယ့် ကုမ္ပဏီကြီးတွေမှာ ကိုယ့်စက်ထဲကနေ Code ကို Github ပေါ် တင် (Push) လိုက်တာနဲ့ တစ်ပြိုင်နက် -
၁။ စက်ရုပ်တွေက Code ကို အလိုအလျောက် စစ်ဆေးတယ် (Testing)။
၂။ အမှားမရှိရင် ဆာဗာပေါ်ကို အလိုအလျောက် သွားတင်ပေးတယ် (Deployment)။
ဒီစနစ်ကို CI/CD (ဥပမာ - Github Actions) လို့ ခေါ်ပါတယ်။ နောက်ပိုင်း App ကြီးတွေ ရေးလာတဲ့အခါ ဒါကို မဖြစ်မနေ လေ့လာရပါမယ်။

## ၅။ ပုံမှန် ပြုပြင်ထိန်းသိမ်းခြင်း (Routine Maintenance)

Web App တစ်ခု ပြီးသွားရင် ပစ်ထားလို့ မရပါဘူး။
- **Logs ဖတ်ခြင်း:** တစ်ပတ်တစ်ခါလောက် ဆာဗာထဲဝင်ပြီး Error Logs တွေ (`journalctl`) ကို ဖတ်ကြည့်ပါ။ ကိုယ်မသိလိုက်ဘဲ Error တက်နေတာတွေ ရှိနိုင်ပါတယ်။
- **Updates:** `requirements.txt` (သို့) `package.json` ထဲက Library တွေကို လုံခြုံရေးအရ ပုံမှန် Update လုပ်ပေးရပါမယ်။ (AI ကို "Library တွေ အသစ်ထွက်မထွက် စစ်ပေး၊ ပြီးရင် Code တွေ ပြင်စရာလိုမလို စစ်ပေး" လို့ ခိုင်းလို့ ရပါတယ်)။
